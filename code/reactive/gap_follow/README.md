# gap_follow

Follow-the-Gap (FTG) reactive controller for the F1TENTH / RoboRacer car. It turns each LiDAR scan into free space, finds the largest gap the car fits through, steers towards the farthest point in it (pulled towards the corridor centre on gentle sections), and sets speed from how sharp the turn is and how narrow the gap is.

It is a standalone reactive driver: LiDAR in, drive command out, no map or localization. It is used as a baseline and for exercising the rest of the stack.

- **Language / build:** Python (`rclpy`, `numpy`), `ament_python`.
- **Node:** `gap_follow_node` (executable `gap_follow_node`)
- **Subscribes:** `/scan` (`sensor_msgs/LaserScan`)
- **Publishes:**
  - `/drive` (`ackermann_msgs/AckermannDriveStamped`): steering angle + speed
  - `/gap_follow/debug_markers` (`visualization_msgs/MarkerArray`): only when `publish_markers` is true
  - `/gap_follow/steering_marker` (`visualization_msgs/Marker`): only when `publish_markers` is true

## Running

```bash
# build (venv active, from the workspace root)
python3 -m colcon build --packages-select gap_follow --symlink-install
source install/setup.bash

# run (simulator already up)
ros2 launch gap_follow gap_follow.launch.py                        # markers off (default)
ros2 launch gap_follow gap_follow.launch.py publish_markers:=true  # with RViz markers
```

Every parameter can be changed while the node is running. The change takes effect on the next scan and is logged:

```bash
ros2 param set /gap_follow_node max_speed 4.0
ros2 param set /gap_follow_node publish_markers true
ros2 param dump /gap_follow_node     # current values, to copy back into the YAML
```

Markers are off by default because building hundreds of `Point` messages per scan in Python takes several milliseconds. When they are on, they are built after `/drive` is published, so they never delay the control output.

### Design

All the algorithm logic lives in small classes that take plain data (numpy arrays, floats) and return plain data. They don't depend on ROS (apart from `MarkerVisualizer`, which builds message objects), so each one can be tested on its own. Each class has a matching `...Config` class holding its tunables. Ranges and angles are `float32` arrays, matching the LaserScan message.

`gap_follow_node.py` is a thin orchestrator. It declares the parameters, copies them into the config objects, owns the subscriber and publishers, and calls the modules in order. All modules are stateless, so a post-set parameter callback simply rebuilds them all from the current values whenever a parameter changes.

## Algorithm

`car_half_width = car_width / 2 + 0.05 m` (half the car plus a safety pad). It is used for both disparity extension and gap trimming.

Each `/scan` message runs these steps in order:

### 1. Preprocess: `ScanProcessor.preprocess`

- NaN → 0 (invalid), ±inf → `max_range`, then clip to `[0, max_range]`
- per-beam angle: `angle_min + i · angle_increment`
- FOV mask: `|angle| ≤ fov_deg / 2`; only masked beams are used for gap finding
- an untouched copy (`clean_ranges`) is kept for steps 2 and 8, which need to see real walls

### 2. Side wall distances: `TargetSelector.compute_wall_distance`

`left_dist` / `right_dist` = the mean of the valid (> 0) `clean_ranges` within `±side_probe_window_deg` of +90° / −90°. If there are no readings, it uses `max_range`. These are used for corridor centering in step 7.

### 3. Disparity extension: `ScanProcessor.extend_disparities`

A disparity is a jump between neighbouring in-FOV beams, `|r[i+1] − r[i]| ≥ disparity_threshold`. At a corner, the beams just past the tip look free, but the car is wide and would clip the corner going through them. So the nearer range is extended across the far side by the number of beams the car's half-width covers at that distance:

```
n = floor(atan2(car_half_width, r_near) / angle_increment) + 1
each of those n beams on the far side: r = min(r, r_near)
```

Disparities are detected on the original ranges, and the extensions are written to a separate output. That way, an extended edge is never mistaken for a new disparity in the same pass, so each extension covers exactly its own `n` beams. The loop is sequential plain Python (about 1080 beams), and the result is written back into the array.

### 4. Safety bubble: `find_closest_point` + `zero_bubble`

- closest point = the smallest range among in-FOV beams with r > 0 (zeros are invalid readings, not obstacles)
- every beam within the bubble around it is zeroed:

```
half_angle = atan2(bubble_radius, d_closest)     # π/2 if d_closest ≤ 0.05 m
zero beams  closest_idx ± floor(half_angle / angle_increment)
```

### 5. Largest gap: `GapFinder.find_max_gap`

A gap is the longest contiguous run of beams with r > 0 that are in the FOV; if there's a tie, the first one wins. If it's shorter than `min_gap_points`, there is no gap. In that case the car brakes: **steering 0, speed 0.3 × `min_speed`**, and a red "NO GAP" marker is shown.

### 6. Edge trimming: `GapFinder.trim_gap_edges`

Each end of the gap is eroded so the target can't sit right next to the wall that bounds it. Each side is sized from its own boundary range, because in a hairpin the two walls are often at very different distances:

```
trim = floor(atan2(car_half_width + gap_edge_margin, r_edge) / angle_increment)   # r_edge ≤ 0.05 → 0.5 m
```

If the two trims together would leave fewer than `min_gap_points` beams, both are scaled down in proportion.

### 7. Target and steering: `TargetSelector`

- **Target:** the farthest beam in the trimmed gap. If several beams share the maximum range, it takes the middle one of those, so `ftg_angle = angle[target]`.
- **Corridor centering.** On gentle sections the car is pulled towards the middle of the corridor. The pull fades out as the turn gets sharper, so sharp turns are left entirely to the gap target:

```
w           = 1 − min(|ftg_angle| / center_blend_angle_deg, 1)
final_angle = ftg_angle + w · center_gain · (left_dist − right_dist)
final_angle = clamp(final_angle, ±max_steering_angle_deg)
```

Here `+` = left (REP 103). If the left wall is farther, the correction is positive, which steers left towards the centre.

### 8. Side safety override: `TargetSelector.side_too_close`

If the car is turning (`|final_angle| > 1e-3`), `clean_ranges` is checked on the side it's turning into, at angles from `side_safety_probe_from_deg` to `side_safety_probe_to_deg` (beside and slightly behind the car). If any valid reading is closer than `side_safety_distance`, the turn would clip that wall. The steering is then forced to **0** and the speed to **`min_speed`**.

### 9. Speed: `SpeedPlanner` + `GapFinder.compute_gap_width`

Two independent limits; the lower one wins:

```
v_steer   = max_speed − min(|final_angle| / speed_scale_angle_deg, 1) · (max_speed − min_speed)

gap_width = Euclidean distance between the (x, y) endpoints of the raw gap's two boundary beams
clearance = max(0, gap_width − car_width)
v_gap     = min_speed + (max_speed − min_speed) · min(clearance / min_safe_clearance, 1)

speed     = min(v_steer, v_gap)       # or min_speed when the side safety override fired
```

The gap-width limit matters because a narrow, needle-shaped opening (a switchback apex) may need only a modest steering angle, yet still needs a hard slowdown. The angle-based limit alone can't tell. The width is measured in x/y, not as an angle, because a tight opening can span a wide angle.

### 10. Publish and timing

`/drive` is published (`frame_id: base_link`). If the scan-to-drive time (wall clock, `time.perf_counter`) exceeds 10 ms, a warning is logged. Markers are built after this, if enabled.

## Visualization (`publish_markers: true`)

All markers are in `base_frame_id` with a 0.3 s lifetime.

| Marker | Topic | Meaning |
|---|---|---|
| Cyan points | debug_markers | processed scan: what the algorithm sees after clipping, disparity extension and the bubble (zeroed beams are hidden) |
| Yellow points | debug_markers | raw largest gap (step 5) |
| Green points | debug_markers | trimmed gap the target is chosen from (step 6) |
| Orange sphere | debug_markers | raw FTG target point, before centering |
| Text (red → green) | debug_markers | commanded speed, red at `min_speed`, green at `max_speed`; shows "NO GAP" in red when braking |
| Arrow (green → red) | steering_marker | final steering angle; longer and redder the harder it turns (`marker_*` params size it) |

## Parameters

All are in `config/params.yaml`, with a comment on each.

| Group | Parameters | Role |
|---|---|---|
| Vehicle | `car_width`, `max_steering_angle_deg` | Car size (sets `car_half_width`) and the physical steering limit |
| Scan preprocessing | `max_range`, `fov_deg`, `disparity_threshold`, `bubble_radius` | Clipping, field of view, corner handling, safety bubble |
| Gap finding | `min_gap_points`, `gap_edge_margin` | Smallest usable gap, and clearance trimmed from its edges |
| Steering / centering | `center_gain`, `center_blend_angle_deg`, `side_probe_window_deg` | Strength of the centering pull, where it fades out, and the side-wall sampling window |
| Side safety | `side_safety_distance`, `side_safety_probe_from_deg`, `side_safety_probe_to_deg` | When a turn is aborted, and where to look |
| Speed | `max_speed`, `min_speed`, `speed_scale_angle_deg`, `min_safe_clearance` | Speed range and the two speed limits |
| Visualization | `publish_markers`, `base_frame_id`, `marker_length_min/max`, `marker_shaft_diameter`, `marker_head_diameter`, `marker_head_length` | Marker toggle, frame and arrow size |

### Current tuning

Tuned in `f1tenth_gym` (Jazzy bridge, async mode) on **Spielberg**, with the scan at **10 Hz** (to match the car's LiDAR) and odom at 100 Hz:

- `max_speed 5.0`, `min_speed 3.0`. There are some oscillations in corners, but it recovers and completes laps.
- `gap_edge_margin 0.7`, `center_gain 0.35`, `center_blend_angle_deg 15`, `min_safe_clearance 0.4`, `car_width 0.30`, `max_steering_angle_deg 24`.

Result with these values: about **75-80 s** per lap on Spielberg.
