# pid_wall

PID wall-following controller for the F1TENTH / RoboRacer car. It holds the car at a fixed distance from one wall (left or right) using two LiDAR rays, steers with a PID controller, and sets speed from how open the track is straight ahead.

It is a standalone reactive driver: LiDAR in, drive command out, no map or localization. It is used for basic driving and for exercising the rest of the stack.

- **Language / build:** Python (`rclpy`), `ament_python`
- **Node:** `pid_node` (executable `pid_node`)
- **Subscribes:** `/scan` (`sensor_msgs/LaserScan`)
- **Publishes:**
  - `/drive` (`ackermann_msgs/AckermannDriveStamped`): steering angle + speed
  - `/pid_wall/debug_markers` (`visualization_msgs/MarkerArray`): rays, target line, status text
  - `/pid_wall/steering_marker` (`visualization_msgs/Marker`): steering arrow

---

## Running

```bash
# build (venv active, from the workspace root)
python3 -m colcon build --packages-select pid_wall --symlink-install
source install/setup.bash

# run (simulator already up)
ros2 launch pid_wall pid_launch.py
```

Every parameter can be changed while the node is running. The change takes effect on the next scan and is logged:

```bash
ros2 param set /pid_node velocity 4.0
ros2 param set /pid_node kp 0.3
ros2 param dump /pid_node            # current values, to copy back into the YAML
```

In RViz/Foxglove add `/pid_wall/debug_markers` and `/pid_wall/steering_marker`.

For mapping runs, `simulation_bringup`'s `mapping_bringup_launch.py` starts this controller with `controller:=pid max_speed:=<m/s>` (its minimum speed is clamped to the maximum).

### Design

All the algorithm logic lives in small classes that take plain data and return plain data. They don't depend on ROS (apart from `MarkerVisualizer`, which builds message objects), so each one can be tested on its own. Each class has a matching `...Config` class holding its tunables.

`pid_node.py` is a thin orchestrator. It declares the parameters, copies them into the config objects, owns the subscriber and publishers, and calls the modules in order. It contains no algorithm logic itself.

## Algorithm

Each `/scan` message runs these steps in order:

### 1. Speed: `WallSpeedPlanner`

Takes the closest range among 5 single beams across the forward cone, at `−c, −c/2, 0, +c/2, +c` (`c = front_cone_deg`):

```
front_min ≥ slow_front_distance  → v = velocity               (clear ahead)
front_min ≤ min_front_distance   → v = min_velocity           (wall/apex close ahead)
otherwise                        → linear interpolation between the two
```

The speed is computed first; step 2 uses it for its look-ahead.

### 2. Wall distance error: `WallErrorEstimator`

Two rays on the side being followed (angles in the LaserScan convention, 0 = straight ahead, + = left):

- **b**: perpendicular to the car, at +90° (left wall) or −90° (right wall)
- **a**: `theta` degrees from b towards the front, at 90° − θ (left) or −90° + θ (right)

Each ray uses `get_range_median` (`median_spread_deg`) to reject single-beam noise.

```
alpha = atan2(a·cos θ − b, a·sin θ)      # car heading relative to the wall
Dt    = b · cos(alpha)                   # current perpendicular distance to the wall
Dt1   = Dt + v · lookahead_time · sin(alpha)   # distance projected ahead, using step 1's speed
error = desired_distance − Dt1           # > 0 → too close to the wall
```

The ray angles are mirrored for each side, so `alpha` and `Dt1` already have the correct sign for either wall. The side only matters for the steering direction (`side_sign`), which is applied in the PID step:

- `+steering_angle` = wheels turn **left** (REP 103 / `ackermann_msgs`)
- left wall: too close → steer right → `side_sign = −1`
- right wall: too close → steer left → `side_sign = +1`

An invalid `wall_side` value is logged as a warning and treated as `left`.

### 3. Time step

`dt` is the time between consecutive scan callbacks, from the node clock. It is 0 on the first scan, and the controller treats any `dt ≤ 0` as 1 ms.

### 4. Steering: `PIDController`

```
integral  += error · dt                  # then clamped to ±integral_limit
derivative = (error − prev_error) / dt   # 0 on the very first sample
scale      = clamp((gain_ref_velocity / v)², gain_scale_min, gain_scale_max)
raw        = scale · (kp·error + ki·integral + kd·derivative)
steering   = clamp(side_sign · raw, ±max_steering_angle)
```

**Gain scheduling (`scale`).** At higher speed, the same steering angle moves the car sideways faster; the lateral response grows roughly with v². With fixed gains, the car is calm at low speed but oscillates at high speed. Multiplying all three gains by `(v_ref / v)²` keeps the loop's natural frequency and damping roughly constant across speeds:

- `kp`, `ki` and `kd` apply exactly as written at `gain_ref_velocity`.
- Gains are larger at low speed and smaller at high speed.
- The clamps keep the scale within a sane range at very low and very high speeds.
- `gain_ref_velocity: 0` turns scheduling off (`scale = 1`).

With the current values (`kp 0.32`, `kd 0.25`, reference 5 m/s, scale in [0.5, 3.0]):

| v (m/s) | scale | kp used | kd used |
|---|---|---|---|
| ≤ 2.9 | 3.00 | 0.96 | 0.75 |
| 3.0 | 2.78 | 0.89 | 0.69 |
| 4.0 | 1.56 | 0.50 | 0.39 |
| 5.0 | 1.00 | 0.32 | 0.25 |
| 6.0 | 0.69 | 0.22 | 0.17 |

`ki` is 0 (no integral term).

### 5. Rate limit: `SteeringShaper`

```
|steering_k − steering_(k−1)| ≤ max_steering_rate · max(dt, 1 ms)
```

This stops a sudden PID jump (a noisy alpha, or a curve caught early by ray a) from snapping the steering in one cycle. At a 10 Hz scan and 3 rad/s, that is at most 0.3 rad of change per scan.

### 6. Publish

`/drive` gets the shaped steering angle and the step-1 speed (`frame_id: base_link`), then the markers are published.

## Parameters

All are in `config/pid_node_params.yaml`, with a comment on each.

| Group | Parameters | Role |
|---|---|---|
| Wall geometry | `wall_side`, `desired_distance`, `theta_deg`, `median_spread_deg`, `lookahead_time` | Which wall, how far from it, the ray layout, noise rejection, look-ahead |
| PID | `kp`, `ki`, `kd`, `integral_limit`, `gain_ref_velocity`, `gain_scale_min`, `gain_scale_max` | Steering law and speed-based gain scheduling |
| Steering limits | `max_steering_angle`, `max_steering_rate` | Physical limit (0.4189 rad = 24°) and smoothing |
| Speed governor | `velocity`, `min_velocity`, `front_cone_deg`, `slow_front_distance`, `min_front_distance` | Cruise speed, corner floor, and where braking starts and ends |
| Visualization | `base_frame_id` | Frame the markers are drawn in |
